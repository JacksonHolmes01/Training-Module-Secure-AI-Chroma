# Authentication (Tokens)

**Authentication** answers one question:

> **Who are you, and can you prove it?**

Chroma cannot answer that question, so the gateway answers it for every request.

---

## How the gateway identifies you

Open `gateway/default.conf` and find this block:

```nginx
map $http_authorization $role {
    default "";
    include /etc/nginx/secrets/tokens.map;
}
```

A `map` is a lookup table. NGINX takes the request's `Authorization` header, looks it up in `secrets/tokens.map`, and stores the result in a variable called `$role`.

Look at the structure of the token map, but **do not print the tokens**. This command hides them:

```bash
sed -E 's/Bearer [A-Za-z0-9]+/Bearer <hidden>/' secrets/tokens.map
```

```
# Generated by bin/setup_secrets.sh. Do not commit.
"Bearer <hidden>" "admin:all";
"Bearer <hidden>" "writer:acme";
"Bearer <hidden>" "reader:acme";
"Bearer <hidden>" "reader:globex";
```

Each token maps to a **role** and a **tenant**, like `reader:acme`. A token that is not in the list gets `default ""`: an empty role.

Then the `server` block checks the result:

```nginx
if ($http_authorization = "") {
    return 401 '{"error":"missing Authorization: Bearer token"}\n';
}
if ($role = "") {
    return 403 '{"error":"invalid token"}\n';
}
```

## Test 1: no token (expected to fail)

```bash
bin/chroma.sh none GET /api/v2/heartbeat
```

### What success looks like (failure is expected)

```
{"error":"missing Authorization: Bearer token"}
[HTTP 401]
```

---

## Test 2: wrong token (expected to fail)

```bash
bin/chroma.sh wrong GET /api/v2/heartbeat
```

### What success looks like (failure is expected)

```
{"error":"invalid token"}
[HTTP 403]
```

- **401** means "you did not say who you are"
- **403** means "I do not accept who you say you are"

## Test 3: valid token (expected to succeed)

```bash
bin/chroma.sh acme_reader GET /api/v2/heartbeat
```

```
{"nanosecond heartbeat":1794463436381002226}
[HTTP 200]
```

## Chroma never sees your token

In the gateway config:

```nginx
proxy_set_header Authorization "";
```

The gateway **removes** the token before passing the request to Chroma. If Chroma (or anything that logs Chroma's traffic) is ever compromised, the tokens are not there to steal.

## Compare with Lesson 4

Run the exact attack from Lesson 4, now aimed at the gateway, with no token:

```bash
curl -s --cacert secrets/server.crt -X POST \
  https://localhost:8443/api/v2/tenants/default_tenant/databases/default_database/collections \
  -H "Content-Type: application/json" -d '{"name": "planted-by-attacker"}'
```

```
{"error":"missing Authorization: Bearer token"}
```

Same attack, now blocked before it reaches Chroma.

## How this differs from authorization

At this point the gateway knows **who** you are. A valid token is not enough to do anything you like, though. The next lesson decides **what** each token is allowed to do.
