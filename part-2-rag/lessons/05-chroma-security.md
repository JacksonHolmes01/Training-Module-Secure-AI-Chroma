# Lesson 5: Chroma Security: Tokens, Roles, and Tenants

In Part 1 you put a gateway in front of Chroma and typed every request by hand. In Part 2 the same gateway sits **inside** the system, between the API and Chroma, and the API is written to use it correctly.

---

## The internal gateway

Open `chroma-gateway/default.conf`. It is the Part 1 gateway with two differences:

| | Part 1 gateway | Part 2 internal gateway |
|---|---|---|
| Who connects | You, from your computer | Only the API, on the `backend` network |
| Transport | HTTPS on `127.0.0.1:8443` | Plain HTTP, never published |
| Writer may create collections | Yes | **No**. Only `chroma-init` (admin) does that |
| Writer may `upsert` | Yes | **No**. Ingestion only adds new records |

Each change removes a permission the app does not need. Upsert can **overwrite** existing records, and ingestion never needs to overwrite, so the writer cannot.

> Plain HTTP is acceptable here only because this hop never leaves the private Docker network on one machine. Part 4 revisits encrypting internal traffic.

## Three tokens, three jobs

`bin/setup_secrets.sh` created three tokens and wrote `secrets/tokens.map`:

```bash
sed -E 's/Bearer [A-Za-z0-9]+/Bearer <hidden>/' secrets/tokens.map
```

```
# Generated by bin/setup_secrets.sh. Do not commit.
"Bearer <hidden>" "admin:all";
"Bearer <hidden>" "writer:lab";
"Bearer <hidden>" "reader:lab";
```

| Token | Held by | Runs | Can |
|---|---|---|---|
| admin | `rag-chroma-init` | Once, at startup | Create the tenant, database, and collection |
| writer | `rag-api`, used only by `/ingest` | All the time | **Add** records to `lab` |
| reader | `rag-api`, used by `/chat` and retrieval | All the time | **Query** and **get** records in `lab` |

## The one-time setup container

Open `chroma-init/init.sh`. It waits for Chroma, then creates `lab → main → documents` with cosine distance, skipping anything that already exists.

```bash
docker logs rag-chroma-init
```

### What success looks like (first run)

```
Waiting for Chroma through the gateway...
created tenant lab
created database lab/main
created collection lab/main/documents (cosine)
chroma-init complete.
```

On later runs it prints `exists` for each step instead. This is called an **idempotent** script: running it twice is as safe as running it once.

## How the API uses the tokens

Open `ingestion-api/app/chroma_client.py`:

```python
writer = _client("writer")
reader = _client("reader")
```

- `insert_doc()` uses `writer`. Only `/ingest` calls it
- `search()` uses `reader`. `/chat` and retrieval call it

The chat endpoint receives the most untrusted input: anyone with the key can type anything. Giving it a **read-only** token means even a successful attack through chat cannot change the knowledge base.

And the tenant:

```python
APP_TENANT = os.getenv("APP_TENANT", "lab")
BASE = f"{CHROMA_URL}/api/v2/tenants/{APP_TENANT}/databases/main"
```

The tenant comes from **configuration**, not from the request. Even if a bug let a request choose a different path, the gateway would still refuse it, because both tokens are locked to `lab`.

## Test the tokens yourself

`bin/chroma_as.sh` sends a request to the internal gateway **from a throwaway container on the backend network**, using one of the lab's tokens. It lets you act as the API would.

Look up the collection ID:

```bash
CID=$(bin/chroma_as.sh reader GET /api/v2/tenants/lab/databases/main/collections/documents | head -1 | python3 -c "import json,sys; print(json.load(sys.stdin)['id'])")
echo "$CID"
```

### The reader cannot add (expected to fail)

```bash
bin/chroma_as.sh reader POST /api/v2/tenants/lab/databases/main/collections/$CID/add \
  '{"ids": ["planted"], "embeddings": [[0]], "documents": ["Planted by a compromised chat endpoint"]}'
```

```
{"error":"this token is not allowed to do that"}
[HTTP 403]
```

### The writer cannot delete or overwrite (expected to fail)

```bash
bin/chroma_as.sh writer POST /api/v2/tenants/lab/databases/main/collections/$CID/delete '{"ids": ["anything"]}'
bin/chroma_as.sh writer POST /api/v2/tenants/lab/databases/main/collections/$CID/upsert '{"ids": ["anything"], "embeddings": [[0]], "documents": ["x"]}'
bin/chroma_as.sh writer DELETE /api/v2/tenants/lab/databases/main/collections/documents
```

All three:

```
{"error":"this token is not allowed to do that"}
[HTTP 403]
```

### The writer cannot create a second collection (expected to fail)

```bash
bin/chroma_as.sh writer POST /api/v2/tenants/lab/databases/main/collections '{"name": "shadow-copy"}'
```

```
{"error":"this token is not allowed to do that"}
[HTTP 403]
```

### No token at all (expected to fail)

```bash
bin/chroma_as.sh none GET /api/v2/heartbeat
```

```
{"error":"missing Authorization: Bearer token"}
[HTTP 401]
```

## Test: a request cannot choose its tenant (expected to fail)

Try to ingest a document while claiming to be another tenant:

```bash
EDGE_API_KEY=$(grep -E '^EDGE_API_KEY=' .env | cut -d= -f2-)
curl -s -X POST http://localhost:8088/ingest \
  -H "X-API-Key: $EDGE_API_KEY" -H "Content-Type: application/json" \
  -d '{"text": "Planted document", "tenant": "other-customer"}'
```

### What success looks like (failure is expected)

```json
{"detail":[{"type":"extra_forbidden","loc":["body","tenant"],"msg":"Extra inputs are not permitted","input":"other-customer"}]}
```

`app/schemas.py` sets `extra="forbid"`, so the unexpected `tenant` field is rejected before any code runs. That is the first layer. The gateway's tenant lock is the second.

---

## A note on token file permissions

The token files are created with permissions `644` (readable by every user on your computer) so that the containers, which run as different users, can read them. That is a reasonable trade-off on a personal laptop and a real weakness on a shared machine. Part 4 shows how to give each container exactly one readable secret instead.
